# Project Spec: Shift Work Calendar (a better Supershift)

This is the product spec. `AGENTS.md` in the repo root defines the engineering rules and is binding. If this file and `AGENTS.md` conflict, `AGENTS.md` and section 0 below win.

## 0. Decisions made after the original spec (these override anything below)

- **ORM:** Drizzle ORM on top of `expo-sqlite`, with migrations generated by `drizzle-kit`.
- **Navigation:** React Navigation only (native-stack + bottom-tabs). No expo-router.
- **State management:** Zustand. SQLite is the source of truth for persisted data.
- **Package manager:** Bun.
- **Icons:** react-native-vector-icons via the scoped `@react-native-vector-icons/feather` package (Feather family).
- **Styles:** live in the same `.tsx` file as the component, via a shared `makeStyles` helper.
- **Design direction:** calm and minimal, easy on the eyes at night. Dusty rose accent (used sparingly). Dark mode is first-class. The main user is a nurse who mostly works night shifts.
- **Default shift templates:** Day (07:00-19:00), Night (19:00-07:00), Off. All editable.
- **iOS notification cap:** iOS allows only 64 pending local notifications, so reminders use a rolling window and a single idempotent reconcile function (see section 5).
- **Coding agent:** work is done mostly by AI coding agents, in checkpointed stages, so the code must be easy to debug later.
- **Testing:** no automated tests and no test frameworks (no Jest). The developer tests manually on real devices.

## 1. Project Overview

Build an application similar to Supershift (Shift Work Calendar), improving on its features and user experience.

Supershift is a shift-work scheduling application that lets users manage work shifts, create repeating rotations, track working hours and earnings, schedule reminders, and view their work schedule in a calendar.

The goal is a polished, reliable shift scheduling app with a strong calendar experience, flexible reminders, offline functionality, and potentially additional features such as advanced earnings tracking and cloud synchronization.

This should be a real product, not merely a calendar UI prototype.

## 2. Critical Technical Constraint

**The app must remain entirely within the Expo Go environment.**

- Use React Native with Expo and TypeScript.
- Do not require ejecting from Expo Go.
- Do not require a custom development client or development build.
- Avoid solutions that require custom native modules or modifications to native Android/iOS projects.
- Prefer Expo SDK packages supported by Expo Go.
- Before recommending a feature, verify that it works within Expo Go.
- If a feature requires a native development build, explain the limitation and suggest an Expo Go-compatible alternative.

The application should work on both Android and iOS as far as Expo Go permits.

## 3. Technology Stack

### Mobile application

- React Native
- Expo
- TypeScript

### Local storage

- SQLite, using `expo-sqlite`, accessed through Drizzle ORM.
- The application should be usable offline without requiring users to sign in.
- Shifts, templates, rotation rules, and reminder preferences should persist locally.

### Notifications

- `expo-notifications`
- Local scheduled notifications for shift reminders.
- The operating system should deliver scheduled notifications without requiring the app to remain open, subject to OS permissions and scheduling restrictions.
- Do not use JavaScript timers as the primary reminder mechanism.

### Optional future backend

- Cloudflare Workers
- Cloudflare D1
- Drizzle ORM

Cloud synchronization, accounts, and collaborative features are future possibilities, not requirements for the initial MVP.

## 4. Core Product Features

### A. Calendar

Build a proper shift-work calendar supporting:

- Month, week, and day views.
- Color-coded shifts.
- Custom shift names and emojis.
- Multiple shifts per day.
- Adding, editing, and deleting shifts.
- Copying shifts between dates.
- Overnight shifts.
- Personal and work calendars.
- Quick shift creation.
- Navigation between dates.
- Reliable handling of dates and time zones.

The calendar should be the primary interface, not a secondary screen behind a dashboard.

### B. Shift Templates

Users should be able to define reusable shift types.

Example:

```ts
type ShiftTemplate = {
  id: string;
  name: string;
  startTime: string;
  endTime: string;
  color: string;
  breakMinutes: number;
  hourlyRate?: number;
};
```

Example templates include Morning, Evening, Night, and Off.

The exact model can be improved during implementation. An off-day entry should be distinguishable from a missing or invalid template.

### C. Rotation Engine

Users should be able to configure repeating schedules, such as:

- Four days working followed by four days off.
- Morning, Evening, Night, Off.
- Custom repeating sequences.
- Rotations anchored to a specified start date.

The rotation engine should calculate which shift applies to any requested date.

Conceptually:

```ts
type Rotation = {
  anchorDate: string;
  pattern: (string | null)[];
};
```

The engine should handle:

- Dates before and after the anchor date.
- Negative modulo correctly.
- Overnight shifts.
- Time zones and daylight-saving transitions where applicable.
- Manual changes to individual generated shifts.
- Editing a rotation without accidentally overwriting user modifications.

The rotation engine must be independent of the UI so that the calendar, reports, and reminders can all reuse it.

## 5. Multi-Reminder System

Users configure **multiple reminders for each shift**, with three reminders as the default:

- 1 hour before.
- 30 minutes before.
- 15 minutes before.

These must not be hardcoded. Users can customize the reminder intervals.

### Reminder preferences model

Use an array of minute offsets.

```ts
type ReminderPreferences = {
  enabled: boolean;
  minutesBefore: number[];
};

const defaultPreferences: ReminderPreferences = {
  enabled: true,
  minutesBefore: [60, 30, 15],
};
```

Examples:

```ts
[60, 30, 15]
[120, 60, 10]
[1440, 60, 15]
[30]
[]
```

The numbers represent minutes before the shift starts. An offset of `1440` means 24 hours before the shift.

The array should be validated, deduplicated, and sorted in descending order. Negative values, invalid values, and past notification times must be rejected or skipped appropriately.

### Customizable reminder UI

The application should provide settings that allow users to:

- Enable or disable reminders globally.
- Select predefined reminder intervals.
- Add custom intervals in minutes.
- Remove existing intervals.
- Have one, three, or more reminders.
- Disable all reminders by using the enabled setting or an empty array.
- Potentially configure different reminder settings for individual shifts.

The default should be `[60, 30, 15]`.

### Reminder scheduling

Use `expo-notifications` to schedule each reminder independently.

For example, if a shift starts at 10 PM:

| Reminder offset | Notification time |
| --------------- | ----------------- |
| 60 minutes      | 9:00 PM           |
| 30 minutes      | 9:30 PM           |
| 15 minutes      | 9:45 PM           |

Each notification should contain:

- A title such as "Upcoming shift".
- The shift name.
- How much time remains before the shift starts.
- The shift ID in notification data.

Use `Notifications.scheduleNotificationAsync()` with a date-based trigger.

Conceptual example:

```ts
const reminderAt = new Date(shiftStartsAt.getTime() - minutesBefore * 60_000);

await Notifications.scheduleNotificationAsync({
  content: {
    title: "Upcoming shift",
    body: `${shiftName} starts in ${minutesBefore} minutes.`,
    data: {
      shiftId,
      minutesBefore,
    },
  },
  trigger: {
    type: Notifications.SchedulableTriggerInputTypes.DATE,
    date: reminderAt,
  },
});
```

Use the installed Expo SDK's actual API and types when implementing this. The example is illustrative, not a complete production-ready scheduler.

### Scheduling lifecycle

The implementation must handle the following cases.

**When creating a shift:**

1. Save the shift to SQLite.
2. Read the applicable reminder preferences.
3. Calculate each reminder time.
4. Skip reminders whose scheduled times are already in the past.
5. Schedule all valid notifications.
6. Persist the returned notification IDs.

**When editing a shift:**

1. Cancel the old notifications.
2. Recalculate the reminder times.
3. Schedule replacements.
4. Persist the new notification IDs.

**When deleting a shift:**

- Cancel all scheduled notifications associated with that shift.

**When reminder preferences change:**

- Update the relevant scheduled notifications.
- Changes affect future shifts that have no per-shift override. Existing per-shift customizations are never silently overwritten.

**When scheduling partially fails:**

- Record successful notification IDs.
- Avoid duplicate notifications during retries.
- Reconcile the actual scheduled notifications with persisted state.

The scheduling operation must be idempotent. Repeated edits must not create duplicate reminders.

**iOS limit (important):** iOS keeps at most 64 pending local notifications. Schedule only the nearest reminders (cap around 60) as a rolling window, and top up on app launch and when the app returns to the foreground. All of the cases above are handled by one reconcile function that compares the desired reminders with the persisted records and the OS's actually scheduled notifications.

### Reminder persistence

Keep two separate concepts:

1. Reminder preferences.
2. Scheduled notification records.

```ts
type ScheduledReminder = {
  id: string;
  shiftId: string;
  offsetMinutes: number;
  notificationId: string;
  scheduledAt: string;
};
```

Use SQLite to persist notification IDs and their association with shifts. Do not rely only on React state or in-memory arrays.

The global preferences define defaults for newly created shifts. Individual shifts may override those defaults.

### Notification limitations

The app must remain in Expo Go.

- Local scheduled notifications are supported.
- Notification permissions must be requested and handled correctly.
- Test on real Android and iOS devices.
- The app should work without a backend.
- Notifications are not guaranteed to arrive at an exact time under every OS, battery, Focus, or permission configuration.
- Do not promise alarm-clock-level reliability or bypass silent mode.
- Do not introduce custom native modules or development builds.

## 6. Suggested Database Entities

The following entities are a starting point:

| Entity                | Purpose                                               |
| --------------------- | ----------------------------------------------------- |
| `shift_templates`     | Reusable shift definitions                            |
| `shifts`              | Actual shift instances                                |
| `rotations`           | Repeating schedule definitions                        |
| `rotation_exceptions` | Per-date skips or replacements of a rotation's output |
| `settings`            | Default reminder settings and app preferences         |
| `scheduled_reminders` | Notification IDs and scheduling metadata              |
| `jobs`                | Optional separate workplaces                          |
| `pay_rules`           | Optional earnings calculations                        |
| `calendars`           | Optional personal/work calendar grouping              |

The final schema should be designed around actual app requirements rather than creating unnecessary tables prematurely.

Shift records should have stable IDs, start and end timestamps, a template reference where applicable, notes, and modification metadata.

Use proper date and time handling. Overnight shifts must end on the next date when appropriate.

## 7. Potential Differentiating Features

These are future improvements, not mandatory MVP requirements:

- Advanced earnings calculations.
- Overtime, holiday, and weekend pay.
- Monthly working-hours reports.
- CSV and JSON export.
- Calendar import/export.
- Home-screen widgets.
- Shift swapping and sharing.
- Optional cloud sync.
- Natural-language shift creation.

Widgets, native alarms, and other platform-specific features must be checked for Expo Go compatibility before implementation. Do not assume that every Expo SDK feature is available in Expo Go or that background work executes at an exact time.

## 8. Development Order

### Phase 1: Foundation

- Set up the Expo project, tooling, theme, and navigation shell.
- Domain layer: dates, rotation engine, reminder math.
- Database schema, Drizzle migrations, repositories, Zustand stores.

### Phase 2: Calendar

- Build the month view first.
- Add shift creation and editing.
- Add week/day navigation.
- Handle overnight shifts and date boundaries.

### Phase 3: Multi-reminders

- Configure `expo-notifications`.
- Request notification permissions.
- Implement customizable reminder arrays.
- Schedule multiple reminders per shift.
- Persist notification IDs.
- Implement cancellation, rescheduling, and reconciliation.
- Test app restarts and edits on real devices.

### Phase 4: Reports and polish

- Add working-hour calculations.
- Add configurable pay calculations.
- Add export and backup.
- Improve interactions and performance.

### Phase 5: Optional expansion

- Explore widgets and system calendar integration.
- Add cloud sync if necessary.
- Add sharing and collaboration.

## 9. Development Principles

- Keep business logic separate from UI components.
- Use TypeScript strictly (never `any`).
- Make the app local-first and offline-capable.
- Avoid unnecessary abstractions.
- Do not hardcode reminder intervals.
- Handle rotation and date edge cases explicitly (negative modulo, DST, overnight). The developer verifies them manually.
- Avoid duplicate notifications.
- Keep the code compatible with Expo Go.
- Verify package APIs against the installed Expo SDK.
- Prefer maintainable, production-quality implementations over quick hacks.
